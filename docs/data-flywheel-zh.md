# llav 数据飞轮与护城河架构（2026-11-12 晚）

> 输入：`jev-value-原文.txt`（a16z 为何给 Jev 75 亿估值：新原语、Jevons 效应、卡住控制流的位置、**需求地图数据飞轮**、agent 控制平面、研究团队、基金逻辑）。用户要求：llav 的网站、后台、数据架构必须把"拆好的问题 schema、调好的阈值、人工审核流程、升级路径、行业/环节/置信度"这些数据收集起来并形成"免费 API → 数据 → 微调 → 垂直服务"的闭环，否则只是一个免费开源服务。

## 1. 诚实的现状审计（改之前）

| 飞轮环节 | 云端架构（`~/llav/web`，改之前） | 结论 |
|---|---|---|
| 请求内容（state / questions / answers） | **不存**，只存用量元数据（时间、key、问题数、延迟、状态） | 没有数据，谈不上飞轮 |
| 客户的结果回传（人工怎么判、最终发生了什么） | 无接口 | 缺"真实结果标签"，这是我们对 Jev 最大的理论优势，却没有入口 |
| 问题 schema / 模板 | 不识别、不聚合 | 没有"需求地图" |
| 阈值与升级路径 | 全在客户代码里，平台看不到 | 没有"卡位"，模型随时可换 |
| 行业 / 环节标签 | 无 | 需求地图没有维度 |
| 同意与隐私 | 无 | 收集了也不能用 |
| 导出到训练 | 无 | 闭环断在最后一步 |

结论：之前的设计是"安全的计量网关"，不是飞轮。本地原型（`~/llav/product`）倒是把完整请求落了 jsonl，但那是单机内测。

## 2. 目标架构（已实现 = ✅，规划 = ◻）

```
客户代码 ──/v1/systemone──▶ 网关 ──▶ 推理后端
               │              │
               │              ├─ ✅ decision_events：request_id、state、questions、answers、延迟、是否带证据（仅在 key 同意时存内容）
               │              ├─ ✅ question_templates：把每个问题归一化成"schema 模板"（类型 + 指令 + 判据，去掉候选内容），计数、首末出现、使用它的 key 数 → 需求地图的"要做什么判断"
               │              ├─ ✅ policies：客户通过 PUT /v1/policy 声明阈值（auto_accept_min / auto_reject_max）与中间档动作（llm / human / second_model）→ 需求地图的"置信度设多少、人工在哪"；有策略时答案里附 tier
               │              ├─ ✅ api_keys.industry / use_case / data_use：行业与环节标签、数据使用同意（免费层默认同意，可关）
               └──/v1/feedback─▶ ✅ feedback：客户回传 accepted / overridden / correct / incorrect / escalated / human_label + 可选金标与下游结果 → 真实标签
                                 ✅ 管理页接口 /api/admin/demand-map：模板排行、行业×环节×同意数、策略分布、反馈分布、事件总量
                                 ◻ 导出管线：D1 → JSONL（我们的训练格式）→ 去重、脱敏、按模板/行业切分 → 评测集 + 训练集 → 新版本 → 按客户灰度
                                 ◻ 大请求体转 R2 对象存储（D1 单行上限 1 MB；现在截断在 900 KB）
                                 ◻ 按 template 的策略（现在只有 key 级 '*'），按客户的校准曲线与自动化率报表
                                 ◻ 条款：免费层"数据用于改进模型"的明示同意；企业层 data_use=0 + 私有部署
```

## 3. 这些数据怎么变成模型与产品

1. **真实标签优先级**：feedback 里的 `human_label` / `correct` / `incorrect` > 下游 `outcome` > 模型自身的分数。每周把带反馈的事件抽成评测集（按客户、按模板），先量"每个置信区间的实际精度"（这正是 lla2 里说的按桶调阈值），再决定是否重训。
2. **按模板蒸馏/微调**：question_templates 按 uses 排名就是"世界在问什么"。前几名模板各自形成一个垂直数据集，用现有的 `train-rerank-listwise.py` / `train-set-judge.py` 在 4B 上做 LoRA；高价值垂直再上 9B / Qwen3.8-27B。
3. **策略数据的用法**：policies 给出每个客户的阈值与升级路径 → 我们能计算"在他们的阈值下我们的精度/覆盖"，并主动建议更优阈值（产品黏性），也能按行业汇总出"该环节通常要 0.9 以上才自动执行"这类知识，写进文档与默认策略模板。
4. **闭环节奏**：免费 API 跑量 → 每周导出 → 评测 → 微调 → `llav-0.x+1` 新版本号（客户锁版本，自主升级）→ 针对某个行业的专用端点（付费）→ 私有化部署（付费）。

## 4. 与 Jev 的对照（护城河在哪）

| | Jev | llav |
|---|---|---|
| 请求内容与 schema | 全部经过 TypeSafe | 经过我们（同意制） |
| 真实结果标签 | 没有入口，训练用 LLM 共识 | `/v1/feedback` 直接收 |
| 阈值/升级路径 | 在客户代码里 | 可托管在平台（policy），答案直接带 tier |
| 可微调 | 否 | 是：按模板/客户微调，权重开源可私有 |
| 第一个垂直 | 通用 | 检索判别（SAG2）、技能胜率（第一客户）、东南亚支付风控（LLaPay） |

## 5. 隐私与合规的硬规则（写进代码与条款）
- 内容存储只在 `data_use=1` 时发生；关闭后只存元数据与模板指纹（模板不含候选文本）。
- IP 只存哈希前 16 位；key 只存哈希；反馈只能标注自己 key 的请求。
- 训练导出前做去重与脱敏（邮箱/电话/卡号正则 + 可选 LLM 脱敏），企业数据不进通用模型，只进该客户的私有版本。
- 条款里写明：免费层数据用于改进模型，企业层可关闭。
